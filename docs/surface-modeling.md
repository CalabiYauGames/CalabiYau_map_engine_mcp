# 表面建模实战：把外部 3D 模型（PMX / GLB）还原成面板

> 面向"把一个真实三维模型（人物、道具、载具）搬进地图"这类任务。
> 本文只讲**拼表面**这条路。想搭方块建筑请看 `modeling-guide.md` 的"方法 A：体素建筑"。

---

## 🎯 先选路线：体素还是面板？

| | 体素（`place_actors` + `fill_box`） | 面板（`place_quads`） |
|---|---|---|
| 适合 | 方块建筑、载具、像素画、任何本来就是方块拼的东西 | 有机曲面：人物、生物、布料、圆雕 |
| 数量级 | 1 格 = 1 块，2 格高人物约 3000~6000 块 | 1 格 = 100cm，2 格高人物 1.5 万~3 万块 |
| 优点 | 轴对齐，绝不互穿，观感"像游戏内建的" | 面积不受格数限制，曲面平滑，能贴图取色 |
| 缺点 | 曲面只能阶梯化，1 格厚外壳在平面上是细环，贪心合并几乎无效 | 面板是薄片，**相邻面板对不齐就会出毛刺** |

**判据**：模型主体如果是"斜面、圆、布"就上面板；如果是"方盒子、机翼、炮管"就上体素。
一艘轴对齐的战斗机用面板反而更差——它本来就是方块。

---

## 🧭 流水线概览

```
PMX/GLB
  ├─ 解析（顶点 / 三角形 / 材质 / 贴图）
  ├─ 坐标系换算：world = (x, -z, y) * scale，落到目标格
  ├─ 平面域生长   → 把三角形聚成"近似共面 + 同材质"的区域
  ├─ 逐区域栅格化 → 每格取一次颜色（必须走 mipmap）
  ├─ 同色贪心矩形合并 → 1 个矩形 = 1 块面板
  ├─ 边界外扩（overlap）→ 相邻面板互相压边，遮缝
  ├─ 高度归一化   → 总高压到目标格数以内
  └─ place_quads 分批落图（每批 ≤ 900）
```

平面域生长是这套方法的关键：**逐三角形建面板会得到"每个三角形一块板"，几万块还互相重叠**。
共面块分解（coplanar patch）对有机模型同样失效——UV 球面上没有两块真正共面。

---

## 🐟 曲面拼接：鱼鳞法（从地图里现成的好模型反推出来的）

地图里如果已经有一个做得好的面板模型，**把它拆开来量一遍**，比凭空调参快得多。
用 `list_actors` 把它的 transform 全读出来，算三件事：面板尺寸、相邻中心距、朝向分布。

实测一个做得很干净的参照模型（同尺寸 Q 版角色，3430 块）：

| 指标 | 参照模型 | 朴素做法（平铺） |
|---|---|---|
| 面板尺寸（中位） | 1.08 × 1.11 cm | 1.4 × 1.4 cm |
| **相邻中心距（中位）** | **0.71 cm** | 0.8 cm |
| 板厚 | 0.11 cm | 1e-4 cm |
| 朝向种类 | 516 种（完全自由） | 自由 |

**关键就一行：中心距 0.71 < 面板宽 1.08**——每块板压住邻居约三分之一。

这就是"鱼鳞"：不是把格子做得更细，而是**让相邻面板互相重叠**。
平铺（partition）时两块板在曲面上必然错开一个 V 形缝，缝里是暗的，远看就是毛刺；
重叠之后缝被上面的板盖住，曲率再怎么变也看不见。

### 怎么实现

```python
# 1) 每块矩形四边都外扩 overlap，而不是只在区域边界外扩
lo_u, hi_u = -overlap, +overlap
lo_v, hi_v = -overlap, +overlap

# 2) 外扩会让同平面的板互相重叠 -> z-fighting，所以给每块板一个
#    沿自身法线的微小偏移（shingle），让"谁在上面"确定下来
hashed = (i * 73856093) ^ (j * 19349663) ^ (width * 83492791)
lift = ((hashed & 0xFFFF) / 65535.0) * shingle     # 0 ~ shingle cm
point = point + normal * lift
```

推荐值：`overlap ≈ 0.35 × cell`，`shingle ≈ 0.2 × overlap`（太小会闪，太大能看出来）。

### 代价与边界

- 重叠让**轮廓边缘的板多探出 overlap**，所以 overlap 要小于 0.5cm，且格子不能太大。
- 板太大会适得其反：翘起量 (L/2)²/(2R) 随 L² 增长，**限边长仍然必须做**（见坑 1a）。
- 重叠不减少面板数，反而略增。要压面板数应该加**格子和限边长**，不能靠取消重叠。

## ⚠️ 踩过的坑（按被咬的次数排序）

### 0. 颜色全错？先查 UV 的 V 轴有没有被翻两次

**这是最容易中招、也最难自己发现的一个。** 症状是"某几个部位变成诡异的颜色"——
实测：腿部采样到 `(2,5,16)`、`(95,111,171)` 这种深蓝垃圾，因为 V 翻反了，UV 落到了
图集里蓝色外套的位置；不翻之后立刻是 `(251,225,214)` 的肤色。

规矩只有一条：

- **PMX 的 UV 原点在左上角**，所以 `y = v * height`，**不要翻**。
- **glTF 的 UV 原点在左下角**，导出 GLB 时才 `v = 1 - v`。

如果代码里既在解析时翻了一次、又在采样时翻了一次，就等于没翻两次 = 读镜像图。
更坑的是**它不会全错**：头发贴图上下颜色接近，翻不翻都对；只有图集上下两端颜色差别大的部位
（腿、鞋、饰品）才会翻车。所以"大部分颜色是对的"完全不能证明 UV 是对的。

自检：按材质统计一次采样颜色的中位数，肉眼过一遍——

```
  6 头发   [231, 202, 154]   ← 金色，对
 11 脸     [254, 244, 235]   ← 肤色，对
 23 腿     [251, 225, 214]   ← 肤色，对（错的版本这里是 [72, 87, 143] 蓝）
 24 鞋子   [ 67,  69,  82]   ← 深藏青，对
```

只要有一个部位的颜色和贴图对不上，就先怀疑 V 轴。

**`preview.png` 不能当基准。** `pmx2glb.py` 导出的预览图（`out/preview*.png`）自己就带着
同一个毛病：它会画成**闭眼 + 蓝色长筒袜**，而真模型是睁眼 + 肤色腿。拿它去校色会把人带反——
看到"腿应该是蓝的"就又把 V 翻回去了。**校色只认按材质统计的采样中位数 + 用户给的参考图**，
不要认 `preview.png`。反过来说，如果成品和 `preview.png` 不一致、但和参考图一致，那是对的。

### 1. 毛刺的两个来源：长条面板翘边（主因）+ 双层薄壳互穿

毛刺（轮廓上伸出的细长针、深色刀片）几乎总是这两件事之一，**先查第一个，它更常见**。

#### 1a. 长条面板在曲面上翘边（主因）

贪心矩形合并只按颜色判据生长，很容易在细长区域（发丝、裙褶、缎带）产出 **1 格宽 × 30 格长** 的条。
一块板是一个平面，曲面上它只能"贴"住中段，两端必然离开表面：

```
翘起量 ≈ (L/2)² / (2R)
```

实测：29cm 长、1.4cm 宽（长宽比 20）的条，落在 R≈20cm 的发梢上，**两端翘出 5.2cm**，
在轮廓上就是一根根针。5.5% 的面板边长超过 8cm，肉眼看到的毛刺基本都来自这批。

**修法：给合并加边长上限 `max_panel_cm`**（本项目的经验值是 **4~6cm**）。

```python
def max_panel_cells(cell_cm, max_panel_cm):
    return max(1, int(math.floor(max_panel_cm / cell_cm + 0.5)))

# 合并时两个方向都别超过这个格数
while True:
    if max_cells and width >= max_cells:
        break
```

效果：最长边 29.12cm → 4.64cm，面板数 31686 → 37771（+19%），毛刺消失。
**代价很小，收益最大，这是调参的第一优先级。**

#### 1b. 双层薄壳互穿（次因）

头发、裙摆、袖口这类布料在模型里通常是**双层薄壳**：外表面和内表面相距约 1.5cm，内表面贴图是深色。
如果平面域生长的 `dist_tol`（到平面距离容差）≥ 壳厚，内外两片会被合并进同一个区域，
栅格化时两片各自成板、互相穿插，**内表面就会整条穿出外表面，看起来像一把深色刀片**。

三种处理，按性价比排序：

1. **减小 `dist_tol`**（壳厚的一半以下，例如 0.6cm）。让内外两片分进不同区域，各自成板，不再互穿。
   代价：面板数上升，且薄壳两侧都要建。
2. **剔除内表面**（推荐配合使用）。从区域中心沿自身法线走 **5~8cm**，如果撞到一个**朝向相反**的面
   （法线点积 < −0.5），说明这块是"夹在三明治里"的那一层，直接整片丢弃。
   实测（0.8cm 格 / 限 4cm）：`gap=5` 剔 569 片 → 37770 块；`gap=8` 剔 720 片 → 35550 块；
   `gap=12` 剔 780 片。三视图覆盖对比：`gap=8` 最差视角只少 **0.35%** 可见像素（`gap=12` 掉到 1.54%）。
   **`gap` 别超过 10cm**：会把下巴底下、腋下、腿缝这些"对着近处另一块面"的真实可见面
   一起剔掉，那些位置就会开洞。判据要卡「撞到的是反向面」而不是「撞到了东西」。
3. **加外扩**（`edge_grow`）。让相邻面板互相压边 0.4~0.8cm，把 1mm 级的缝盖住。

> 反直觉的一点：**单纯把格子调小并不会自动消除互穿**，它只是把刀片切得更碎。
> 真正管用的是「限边长」（1a）+「剔内层」（1b）这两刀。

### 2. `dist_tol` 是为省面板调的，省下的都付了毛刺

把 `dist_tol` 从 0.8 提到 1.6 能把面板从 24.5k 压到 15.2k，但 1.6 ≥ 壳厚 1.5，毛刺立刻满屏。
**先按壳厚定 `dist_tol`，再用格子尺寸和合并去省面板**，不要反过来。

### 3. 区域生长必须限定"同材质"

眼睛、眉毛、嘴是贴在脸上的**近共面贴花层**，距离只有 0.5~1mm。
如果不限制材质，眼睛区域会长到整张脸上，然后栅格化时用虹膜色涂满半张脸、或者眼睛整个丢格。
生长时同时判断 `angle_tol`、`dist_tol` 和 `material_of[tri]` 三者相等。

贴花还要**沿法线前移**一点（`decal_bias`，0.3~0.5cm），否则和脸共面打架。
判断贴花的办法：材质名里含 `眼/瞳/眉/口/齿/舌/睫` 或 `eye/brow/mouth/lash/pupil`。

### 4. 取色必须走 mipmap

按格子尺寸点采样贴图，在 0.8~1.4cm 的格子上必然走样：脸上会铺满**棋盘状暗斑**。
按格子的贴图足迹算 mip 层级：

```python
def mip_level(cell_cm, texels_per_cm, bias):
    footprint = max(1e-6, cell_cm * texels_per_cm)
    return max(0, int(math.floor(math.log2(footprint) + bias)))
```

`bias` 取 **−1.5 ~ −3.5**。取 0 会把眼睛糊成一团，取 −4 又会重新出暗斑。
**UV 的 V 轴要先翻转**（`v = 1 - v`），否则整张贴图上下颠倒。

### 5. `place_quads` 的角点顺序是 A, B, D, C

不是 A, B, C, D。传错会报 `ALL_QUADS_INVALID: Edges 0-1 and 0-2 are not perpendicular`。
也就是四个角要按 **(u0,v0), (u1,v0), (u0,v1), (u1,v1)** 给，第 2、3 个角是"相邻边"而不是"对角"。

```python
def quad_corners(u0, v0, u1, v1):
    return ((u0, v0), (u1, v0), (u0, v1), (u1, v1))
```

**量面板尺寸时同样会踩这个顺序**：`vertices[0]` 是角 A，`vertices[1]` 和 `vertices[2]`
是它两侧的**边**，`vertices[3]` 才是对角。用 `dist(v1, v2)` 量出来的其实是**对角线**，
会把面板虚报大约 1.4 倍（实测 4.17cm 的边被量成 5.90cm）。正确写法：

```python
a, b, c = quad["vertices"][0], quad["vertices"][1], quad["vertices"][2]
edge_u = dist(a, b)   # 边长
edge_v = dist(a, c)   # 边长
```

### 6. 批量落图用 `color_linear_rgb`，不是 `color_srgb`

`place_quads` / `place_actors` 的批量版本只认 `color_linear_rgb`（0~1 浮点）。
`color_srgb` 只在单发的 `place_actor` 里存在。用错会**静默失败**：`errors` 里有条目但 `placement_errors` 是空的。

### 7. 写完之后不能立刻截图

`place_quads` 返回成功只代表数据进了状态，**渲染批次是异步重建的**，1 万块面板要 6~40 秒才出画面。
立刻 `capture_view` 会拍到空帧或旧机位。
`set_camera` 同理：设完要**轮询 `get_camera` 回读**，确认机位真的到了再拍。

```python
for _ in range(20):
    await asyncio.sleep(0.35)
    live = await client.call("get_camera")
    at = live["camera"]["position"]        # 注意是嵌套结构
    if abs(at[0] - x) < 0.05 and abs(at[2] - z) < 0.05:
        break
```

`get_camera` 返回的是 `{"camera": {"position": [...], "target": [...]}}`，**不是**平铺的 `position`。

**更狠的一种情况：不是"慢"，是"根本没重建"。** 实测删掉一批 actor、再在原处附近放上新的，
`list_actors` 立刻就是新数据（数量、坐标、颜色全对），但 `capture_view` 连续多次、
跨好几分钟都还在画**已经删掉的那批旧几何**，而且新几何完全看不见。

判据很简单：**如果"数据对、画面不对"，先怀疑渲染滞后，不要怀疑自己写错了。**

- 删掉的那批还在画 + 新放的看不见 → 渲染层没重建。
- 让编辑器**重新加载页面**（重开或刷新）后，画面立刻和新数据一致。

所以做「搬位置 / 换内容」这类删了再放的改动，别在同一会话里靠截图验收几何，
**先读数据确认，再重载后拍图**。原地新增（没删东西）通常没这个问题。

### 8. 面板厚度是 1e-4 cm，不要试图"加厚"

`place_quads` 内部把每个四边形转成物品 7 的变换，厚度固定 `1e-4 cm`（`scale.x = 4e-6`）。
薄到没有体积，所以**没有"侧面"**——从侧后方看是一片纸。
这既是优点（不会像体素那样凸出轮廓）也是缺点（背面不可见，绕到背后要有另一片）。
想要双面观感就内外各建一层，但那正是坑 1 的来源，慎用。

### 9. `list_actors` 分页用 `offset` / `limit`，单页 ≤ 500

- 不是 `cursor`，传 `cursor` 会一直返回第一页（曾据此把 15228 块数成 374 块）。
- `limit` 太大（> 约 500）会撞 SSE 帧上限：`SSE stream failed: exceeded the 1048576 byte limit`。
- 统计总量要循环到返回条数 < limit 为止。

### 10. `read_only` 与 `editing` 是两个字段，卡写入的是 `editing`

写操作要求 `get_state.editing === true`，否则 `EDIT_MODE_REQUIRED`。
另有一个 `read_only`，某些地图（例如 `Native game mode 0` 的地图）会整体只读，
任何写入都报 `READ_ONLY: Native game mode X is unsupported by native-v7-default.`。
遇到这个不要反复重试，**换一张地图**——这是地图本身的能力限制。

### 11. 自适应模式不能和 `target_size` 一起用

`place_actors` 的 `mode=adaptive` 要求 `mode=full-size`；两个一起传会直接报错。
而体素（1 体素 = 1 格）在"总高 2 格"的约束下根本用不了 adaptive，只能老老实实算格子。

### 12. 从 GLB 走内置导入时，`alphaMode: MASK` 会让表面拟合全拒

引擎的 `plateSafeForMaterial` 认为 MASK 材质不适合用薄板表现，于是整模型退回体素。
而 Blender 导出的 GLB 常常给**所有**材质都写 `alphaMode: MASK`。
判定应该按**实测透明纹素比例**来（该模型 25 个材质 clear 比例全是 0，即全不透明），不要信 `alphaMode`。

### 13. `place_quads` 的 roll 手性存疑（未定论）

内部 `quad_to_transform()` 用
`roll_rad = atan2(-dot(u, z_neutral), dot(u, y_neutral))`。
用右手系反推，输入角点最大偏差 **25.8cm**；把 roll 取反后偏差 **0.00cm**（60 组随机朝向实测）。
但实际落图后模型整体没有散架，说明渲染端可能是左手系、与这段代码自洽。
**结论：轴对齐面板（roll = 0 / ±90°）不受影响；只有斜置面板要注意。**
真要做斜置精细件，先放一块探针、截图量一下，再批量。

### 14. `scale` 是相对 100cm 的倍数，不是绝对值

物品 7 的本地尺寸：X 厚度 −25..0cm，Y/Z ±50cm。`scale = 0.5` 就是 50cm 宽。
所以 1cm 的面板 = `scale.y = 0.01`。`place_quads` 会自己算，手写变换时别把 cm 直接填进 `scale`。

### 15. 高度归一化要在最后一步做

先把模型缩放到目标高度（例如 197cm）再归一化到 199.5cm，是两次缩放。
只做一次：`scale = target_height / (max(y) - min(y))`，落图前再按实际 bbox 夹一次，确保 **≤ 2 格**。
2 格 = 200cm，留 0.5cm 余量，因为面板有厚度和朝向误差。

### 16. 面板上万块时，`EDITOR_BUSY` 会变成永久卡死

- 一次 `delete_region` 删 3 万块、紧接着 `place_quads` 放 3 万块，编辑器会在重建渲染批次时
  崩到 `get_state.phase == "error"`、`busy_reasons == ["error"]`。
  这时**所有写操作**（包括 `undo`、`select_actors`）都返回 `EDITOR_BUSY`，
  但 `capture_view` 仍然正常出图——所以从截图上完全看不出已经卡死。
- **只能由人在编辑器里把那个错误提示关掉**，MCP 侧没有任何工具能清。
- 预防：单次删除 + 放置的总量控制在 **2 万块以内**；分多次小批量做；
  每批之间读一次 `get_state`，`phase != "ready"` 就停下等。
- 顺带一提：地图里那个做得好的参照模型只有 3430 块。**2 格高的人物做到 1.5 万块已经够细**，
  3 万块以上的收益远小于它带来的风险。

### 17. `list_actors` 里的 `scale` 是「局部尺寸」，不是世界半长

`transform.scale` 给的是这块板沿**自身三个局部轴**的尺寸（单位米），顺序是
`(厚度, 宽, 高)`，**不是**世界 X/Y/Z 的半长。物品 7 的板厚固定 1e-4 cm，
所以 `scale[0] ≈ 4e-6`，宽度和高度在 `scale[1]` / `scale[2]` 上。

从 actor 反推几何时如果按「世界半长」去乘 `scale[0]`，宽度会算成 0，
每块板都退化成一条竖线——**这个错看起来像数据坏了，其实只是取错了分量**。

```python
w = t["scale"][1] * 100.0   # 宽（cm）
h = t["scale"][2] * 100.0   # 高（cm）
# 板厚 t["scale"][0] * 100 ≈ 4e-4 cm，没有实用价值
```

### 18. `set_camera` 的单位是**米**，不是厘米

`get_camera` 返回 `position [-20.79, 1.68, -23]`——米。把建模用的厘米
（`-1900, 240, -2800`）直接喂给 `set_camera`，相机会飞到 2.8 km 高空，
截图是一整片天空，而且**不报错**。

另外相机是 `(X, 高度, 深度)` 三个分量，深度 = `−cell_y`。
想知道「往哪边挪能把物体推到画面中间」，**一次拍三个相差 2m 的 X 机位直接看**，
比在纸上推坐标系快得多，也不容易推错。

### 19. 标牌文字别用眼睛验收，用 actor 反解位图

5×7 点阵在 4cm 格、7~8m 距离下每个字形只有 5px 高，**D 会看成 F，E 会看成 A**。
我曾据此判定「标牌写错了、要重放」，实际数据一直是对的，白折腾一轮。

正确做法是把板子反解回位图，再和候选文字逐格比对（脚本见
`_michele_build/decode_sign.py`）：

```python
text = [a for a in plates if abs(a["transform"]["scale"][2] * 100 - CELL) < 0.2]
left = min(a["transform"]["location_cm"][0] - a["transform"]["scale"][1] * 50 for a in text)
top  = max(a["transform"]["location_cm"][2] for a in text) + CELL / 2
# 逐板把 (行, 列) 填进集合，再和 font5x7.bitmap(候选文字) 求差集
print("EXACT" if expected == actual else "mismatch")
```

**先按高度把底板滤掉**（底板 132cm 高，不滤会糊满一整行）。
判据用「`actual == expected` 全等」，不是「看起来像」。

### 20. 标牌要避开邻居模型的遮挡通道

标牌是一块单面薄板。放在邻居模型正后方，换一个机位就会被完全挡住——
从正面看它好好的，换个角度只剩半行字。

落标牌前先 `list_actors` 读一遍邻居的 X / 深度包围盒，把牌子放在
**模型和邻居之间没有重叠投影的一侧**。标牌本身很便宜（三行字 ≈ 250 个 actor），
挪位置只要删掉重放，别在错误的位置上凑合。

## 📊 面板用量对照表（2 格高人物实测）

问「这套参数要花多少个 actor」时看这里，别猜。全部是同一份 PMX（Q 版米雪儿，
13 064 三角形 / 25 个材质）在 199.5cm 总高下的实测值。

### 一、体素 → 面板：省了多少

**先记住一件事：实际性能只和 actor 数量有关，和三角形数无关。** 引擎按 actor 建实例批次，
一块板和一个方块都算 1 个 actor；三角形数只影响单个 actor 的网格大小，不进入批次的成本模型。
所以下面这张表**只看第二列**。

| 做法 | **actor 数** | 三角形 | 备注 |
|---|---|---|---|
| 体素外壳 | 34 222 | 410 664 | 基线 |
| 面板（`panels_final`） | **15 229** | 30 458 | actor 少 **55%** |
| 面板（1.2cm 鱼鳞版） | **18 369** | 36 738 | 为消缝调细了格子，比 1.5 万多 3 千 |

三角形那一列（方块 12 个 / 板 2 个）只说明「一块板比一个方块更省网格」，
**它不是性能指标**，别拿它当优化目标。真正要压的是第一列。

### 二、格距 `cell_cm` → 面板数

固定 `tol 10 / grow 0.5 / dist 0.9 / bias −1.2 / maxp 5 / ov 0.45 / sh 0.08 / cull on`，
只动 `cell_cm`：

| `cell_cm` | 面板数 | 中位面板 | p95 边长 | 最长边 |
|---|---|---|---|---|
| 0.9 | 25 649 | 1.80 × 2.70 | 6.30 | 6.30 |
| 1.0 | 23 392 | 1.95 × 2.95 | 5.99 | 5.99 |
| 1.1 | 20 330 | 2.10 × 3.09 | 6.59 | 6.59 |
| 1.2 | 19 373 | 1.79 × 2.39 | 5.98 | 5.98 |
| 1.3 | 17 379 | 2.39 × 2.59 | 6.47 | 6.47 |
| 1.6 | 14 280 | 2.82 × 3.17 | 6.34 | 6.34 |
| 1.8 | 12 089 | 3.56 × 3.56 | 7.11 | 7.11 |

**曲线不是干净的 1/cell²**，两个原因：

1. 面板数是整数格量化的，`max_panel_cm` 也要取整成格数，相邻档位会互相追平；
2. 面板数有个**地板**：平面域生长的区域数是固定的（约 2 700 个），每个区域至少一块板。
   格子再粗也压不到 2 700 以下。

所以从 1.2cm 调到 1.8cm（格子面积 ×2.25）面板只降 38%，不是降 55%。

### 三、单旋钮的代价（`cell_cm` 固定 1.2，基准 19 373）

| 改动 | 面板数 | 相对基准 | 最长边 | 说明 |
|---|---|---|---|---|
| `max_panel_cm` 不设限 | 15 776 | −19% | **25.12** | 长条翘边，针状毛刺的来源 |
| `max_panel_cm = 8` | 16 665 | −14% | 9.57 | 仍有可见尖刺 |
| `max_panel_cm = 5` | 19 373 | 基准 | 5.98 | 推荐起点 |
| `max_panel_cm = 3` | 21 994 | +14% | 4.78 | 毛刺基本消失 |
| `cull_back = 关` | 22 109 | +14% | 5.98 | 内表面全留下，纯浪费 |
| `overlap + shingle` | 19 373 | **0%** | 5.98 | **白拿**，只改观感 |

两条结论：

- **`max_panel_cm` 才是毛刺旋钮，`cell_cm` 不是。** 不设限时最长边 25cm、19% 的面板超过 8cm；
  限到 3 就是 4.78cm、一块都不超 6cm。代价只有 +14% 面板。
- **`overlap_cm` / `shingle_cm` 完全不增加面板数**（19 373 → 19 373）。
  它们只把每块矩形往外扩、沿法线抬一点，几何体数量不变。**消缝不要用调细格子去换。**

### 四、几档成品的实测对比

| 版本 | cell | maxp | 面板数 | 中位面板 | 最长边 | >6cm 占比 |
|---|---|---|---|---|---|---|
| 已落图 | 1.2 | 5 | 18 369 | 2.24 × 2.39 | 5.98 | 0% |
| 上一版 | 1.4 | 6 | 14 716 | 2.58 × 2.78 | 6.96 | 25% |
| 低毛刺 | 1.4 | 3 | 21 663 | 2.58 × 3.78 | **4.17** | 0% |
| 低毛刺 | 1.5 | 3 | 19 253 | 2.73 × 3.97 | 4.47 | 0% |
| 低毛刺 | 1.6 | 4 | 14 091 | 2.93 × 3.18 | 6.35 | 33% |

**1.4cm + `maxp 3` 是「毛刺最少」的那一档**（最长边 4.17cm，全场没有一块超过 6cm），
代价是 2.1 万块。想同时压面板数，用 1.5cm + `maxp 3`（1.9 万块，最长边 4.47cm）。

### 五、怎么读「毛刺」这件事

实测下来毛刺有两个独立来源，别混：

1. **长条翘边**（针状、单根突出）→ 由 `max_panel_cm` 控制，看「最长边」这一列。
2. **鱼鳞起伏**（整体一层细密的鳞状感）→ 由 `shingle_cm` 控制，和面板数无关。
   面板越小，同样的 `shingle` 相对起伏越大，看着越「毛」。

所以「面板多的版本反而更毛」是正常的：不是格子在作怪，是 `shingle` 相对变大了。
要压这一层，**先降 `shingle_cm`（0.1 → 0.05），而不是去改 `cell_cm`**。

## 💰 Actor 预算：先定上限，再挑参数

**同屏 5 000 – 10 000 个 actor 是舒适区。** 实测 7.5 万块进游戏会明显卡顿；
这是硬约束，不是审美偏好。所以建模的顺序必须反过来：

> 先按预算选 `cell_cm` 定 actor 数，再用 `max_panel_cm` 把毛刺压下去。

反过来做（先追细节、最后才看数量）一定会超预算，然后被迫整体降档、返工。

### 低模档位实测（2 格高人物，`cull` 开，`maxp` 按 2 格取整）

| `cell_cm` | actor 数 | 最长边 | 观感 |
|---|---|---|---|
| 1.2 | 18 369 | 6.0cm | 高模，面部干净 |
| 1.6 | 14 280 | 6.3cm | 高模下沿 |
| 1.8 | 12 089 | 7.1cm | 仍超预算 |
| 2.2 | 10 660 | 6.6cm | 预算上限 |
| 2.5 | 8 882 | 7.5cm | **中档，推荐** |
| 2.8 | 7 727 | 8.4cm | **低模，推荐**（早期单机质感） |
| 3.0 | 7 039 | 9.0cm | 低模下限 |
| 3.2 | 6 355 | 9.6cm | 再粗就认不出角色了 |

注意这张表**不是单调的**：2.0cm（`maxp 4`）出 12 298，比 1.8cm（`maxp 5`）的 12 089 还多。
因为 `max_panel_cm` 会被取整成格数（`round(maxp/cell)`），换档时两个旋钮同时在动。
**要比较格距，必须把 `maxp` 锁死。**

### 低模不等于有毛刺

粗格距不会自己产生针状毛刺——毛刺永远来自**长条面板**。
`max_panel_cm` 在低模档照样要设（按 2 格取：2.5cm→5、2.8cm→5、3.0cm→6），
设了之后 3cm 格的最长边也只有 9cm，轮廓是「方块感」而不是「尖刺感」。

反过来，**不设 `max_panel_cm` 的 3cm 格一样会出 25cm 长条**，照样满身针。
分辨率降下来只让台阶变粗，不会让长条消失。

## 🎯 `decal_cell_cm`：只给眼/眉/嘴用细格

低模最大的损失不是身体，是脸。眼白/瞳孔/睫毛是几个独立材质，在粗格下每个只有 2~3 格，
直接糊成两块深色斑——比身体变方块难看得多。

解法是给这些「贴片区域」单独一个更细的格子。`is_decal()` 已经按材质名识别
（`眼/瞳/眉/口/齿/舌/睫`、`eye/brow/mouth/lash/pupil`），让它们取
`min(region_cell, decal_cell_cm)` 即可。

**代价极小，因为贴片区域本身很小**（全模型只有 12 个）：

| 配置 | actor 数 | 相对不开 |
|---|---|---|
| 3.0cm，`decal_cell` 关 | 6 930 | — |
| 3.0cm，`decal_cell=1.2` | 7 039 | **+109（+1.6%）** |
| 3.0cm，`decal_cell=0.9` | 7 126 | +196（+2.8%） |
| 2.8cm，`decal_cell=1.2` | 7 727 | +112（+1.5%） |

**1.5% 的预算换回整张脸，这是低模里性价比最高的一刀。** 经验值取 `decal_cell ≈ cell/2`，
再细收益就很小了。

### 为什么不用 `cells_target` 做「头细身粗」

`cells_target` 是**每区域目标格数**，它只会把**小区域**往 `cell_min` 推——而小区域恰恰有
两千多个。实测 `cell 3.0 / cell_min 2.0 / cells_target 800` 得到 **9 999 块**，
比同格距不开自适应的 6 930 还多。**它是往细里跑，不是往粗里跑。**
要做「局部细」就用 `decal_cell_cm`，别碰 `cells_target`。

## 📐 参数速查

| 参数 | 含义 | 推荐起点 | 备注 |
|---|---|---|---|
| `cell_cm` | 栅格尺寸 | 0.8 ~ 1.4 | 越小越平滑，面板数按面积/`cell²` 增长 |
| `cell_min` | 区域自适应下限 | 0.3 ~ 0.4 | 眼睛等小岛用更细的格 |
| `cells_target` | 每区域目标格数 | 900 ~ 1200 | 每区域独立算格子尺寸，避免"全模型一个格" |
| `angle_tol` | 生长法线容差（度） | 25 | 太大把转折面糊成一片 |
| `dist_tol` | 到平面距离容差（cm） | **≤ 壳厚一半**，0.5 ~ 0.8 | 见坑 1、坑 2 |
| `edge_grow` | 面板外扩（cm） | 0.4 ~ 0.8 | 盖住相邻板之间的缝 |
| `max_panel_cm` | **单块面板边长上限（cm）** | **4 ~ 6** | **防毛刺第一优先级**，见坑 1a |
| `overlap_cm` | **每块板四边外扩（cm）** | **0.35 × cell** | **鱼鳞重叠，消缝**，见"鱼鳞法" |
| `shingle_cm` | 每块板沿法线的错位（cm） | 0.2 × overlap | 让重叠不 z-fighting |

| `decal_cell_cm` | **眼/眉/嘴单独用的细格（cm）** | **≈ cell/2** | **低模保脸的关键，+1.5% 预算**，见「`decal_cell_cm`」一节 |

## ✅ 落图前自检清单

1. **包围盒**：`max(z) - min(z) ≤ 200cm`？超了就是没归一化。
2. **面板数**：落在 **5 000 – 10 000** 之间？这是同屏流畅的硬预算，超过 1 万进游戏就卡。
   先按这个数选 `cell_cm`，再回头调 `max_panel_cm` 压毛刺。
3. **角点顺序**：A, B, D, C？随机抽 3 个四边形，算一下 0-1 和 0-2 两条边是否垂直。
4. **颜色范围**：`color_linear_rgb` 三个分量都在 0~1？sRGB 的 0~255 会被截断成白色。
5. **落图分批**：每批 ≤ 900，读回 `placed_actors` 和 `placement_errors` 两个字段。
6. **等渲染**：落完等 10 秒以上再截图；`set_camera` 后回读 `get_camera` 确认
   （注意 `set_camera` 收的是**米**，见坑 18）。
7. **三视图**：正、侧、背各拍一张，背面最容易暴露"只有单面"的问题。
8. **标牌**：文字用 actor 反解位图逐格比对（见坑 19），不要用肉眼读截图；
   机位要能同时框住模型和标牌，别让邻居模型挡住（见坑 20）。

## 🔌 关于 MCP 连接方式

**stdio 拉起**（推荐给自动化脚本）：

```bash
uv run python -m calabiyau_map_engine_mcp --transport stdio
```

即使 `--transport stdio`，服务端**仍会在 `127.0.0.1:8765` 开 HTTP 监听并保留 `/bridge` WebSocket**，
所以浏览器编辑器照常连得上。stdio 与 http 两个 task 用 `asyncio.wait(FIRST_COMPLETED)` 并行，
任何一个结束就整体退出。

刚拉起的服务端 registry 是空的，编辑器需要几秒重连 WebSocket。
**必须轮询 `list_sessions` 直到非空**，否则第一次 `get_state` 会报 no browser paired。

```python
async def wait_for_browser(bridge, timeout=60):
    deadline = time.time() + timeout
    while time.time() < deadline:
        found = (await bridge.raw("list_sessions")).get("sessions") or []
        if found:
            return found[0]["browser_session_id"]
        await asyncio.sleep(1.0)
    raise RuntimeError("no browser paired")
```
